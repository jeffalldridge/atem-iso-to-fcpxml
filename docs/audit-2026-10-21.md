# Product review — October 21, 2026

Two passes made the same day, both local and unreleased. The second was a fresh critical review that used the real app, the real website in a browser, and the real GitHub release rather than trusting the first pass. Nothing was pushed, released, deployed, or signed, and no signing credential or repository setting changed. [validation.md](validation.md) records exactly which checks ran and which did not.

## Assessment

The product is sound and small: keep the compound-angle multicam output, explicit overwrite consent, local-only processing, and the lack of dependencies. The first pass improved the native controls and hardened several inputs. The second found that the larger weaknesses were still at the edges: arithmetic on corrupt media, lifecycle behavior nobody had watched in the real app, a window that did not say where its file would go, a missing Close command, and public copy that had drifted from the product.

## Second pass: what was found and changed

| Severity | Finding | Change and evidence |
| --- | --- | --- |
| High | `Rational` did fixed-width `Int` arithmetic, so a corrupt header with an extreme timescale, frame count, sample rate, or time reference could trap the Swift engine. The Python reference had no limits at all. | Both engines now reject media outside the same documented ranges ([architecture.md](architecture.md)); `Rational` computes in 128 bits and reduces before narrowing. Regression tests in both languages. A differential header fuzz (`scripts/fuzz_media_headers.py`, about 2,800 iterations over several seeds) found no signal exits and no Python/Swift disagreement after the change. The fuzz run against the old code found six disagreements but no trap, so the unit tests and the extreme cases above, not the fuzz, are the evidence for the overflow fix. |
| High | The Swift MP4 reader walked every top-level box of a file before looking for `moov`; Python stops at `moov`. A file with 12 million trailing boxes took 33 seconds in Swift and 0.09 in Python, and an invalid box after `moov` was an error in Swift only. | Swift now stops at `moov`. Regression tests in both languages. |
| Medium | Closing the window while a recording was *loading* left a windowless app for the whole load and then quit silently. | Only conversion defers Quit now. Verified in the real app: closing during a slow load quits at once; during a slow conversion the file is published whole and the app then quits; during a conversion that fails the window returns with the error. These used a synthetic recording padded with millions of empty boxes, not a slow external disk. |
| Medium | The app could be automatically terminated by macOS after its window closed during a conversion. | While reading or writing, the app holds a `ProcessInfo` activity that disables automatic termination and App Nap. |
| Medium | Nothing said where the file would be written until it had been, and an existing file surprised people with a dialog. | The action bar states `<name>.fcpxml` and where it goes, and says up front when it already exists. |
| Medium | Every failure was titled "Something Went Wrong". A multi-session `.drp` told app users to use a command-line flag. | Failures name what failed and what to do; failed conversions say the recording was not changed; the session message explains the command-line option; a missing recording suggests checking the drive. |
| Medium | Replacing the save menu group removed **Close** (⌘W) from the File menu. | Restored; added Show in Finder and Open in Final Cut Pro to the File menu. |
| Low | The empty window had an empty bottom bar with a lone button. Timeline labels could be cut off mid-word. | One centered **Choose Recording…** button; labels are drawn only when the whole name fits. Camera rows have an explicit accessibility label and the color swatch is hidden from VoiceOver. |
| Low | The Quick Action ended silently if `open` failed, never looked for a renamed or moved app, and did not say which converter it carried. | It tries both Applications folders, then the bundle identifier, then its embedded converter; the workflow's Info.plist carries the converter version. A test checks the generated script parses and the lookup order. |
| Low | The website's download button led to the release page; the size said 2 MB (it is 2.8 MB); social alt text described a different tagline than the card; the description was too long; the one-session limit was missing; an image note and an unused 512-pixel icon were published. | Fixed. The site tests now also check declared image sizes, real transparent corners, the installer link, and title and description lengths. |
| Low | `AGENTS.md`, `CONTRIBUTING.md`, the bug template, and `website-handoff.md` were thin, conversational, or stale. | Rewritten; feature-request and pull-request templates added. |

Documentation and tests also gained: written audio checked against the window's choices (every WAV the choices imply appears exactly once; nothing else does), the destination note, the session explanation, and the quit policy during a read.

## Decisions

- **No native session chooser.** Multi-session logs were never verified on a real stop-and-start recording, and how later sessions name their media is inferred. A chooser built without that evidence would risk converting the wrong take. The refusal now says what to do. Add one when a real multi-session recording is available.
- **No automatic updater, and no update check.** The app makes no network requests, which is a promise in [SECURITY.md](../SECURITY.md). A user-triggered "check for updates" request would be small, but it would break that sentence, so the menu item only opens the releases page. A real updater (signature verification, version comparison, rollback, an appcast and key to guard) is far more maintenance than a free single-purpose tool warrants.
- **No wholesale redesign.** The window already follows Compressor's pattern (summary on top, three choice panes, action bar at the bottom) with standard controls. The changes above fix what the real app showed.

## Still open

1. **Release workflow.** The `v1.1.0` run skipped signing, notarization, and publishing; the assets were attached separately. The current workflow has never published a release. Review the first real run closely. Suggested hardening, not done because it concerns signing and publishing: publish a draft first, check that the tag commit is on `main`, scope `contents: write` to a separate publish job, and pin third-party actions to commit hashes.
2. **Published download.** I did not download the disk image; clean-download Gatekeeper acceptance, notarization, and a replacement of a running installation are unverified.
3. **Final Cut.** No new import was done. No XML shape changed, and byte parity with the verified Python output holds on every parity scenario. I did not click Open in Final Cut Pro because it would import a test event into the maintainer's real library.
4. **Native acceptance not done:** VoiceOver, Full Keyboard Access, light appearance, Reduce Motion and Transparency, small and multiple displays, drag and drop from Finder, an actual slow external disk, exFAT, a read-only or full destination, macOS 15, and real Intel hardware.
5. **Real recordings.** Other ATEM models and frame rates, keys and non-mix transitions, and multi-session logs remain synthetic-only.
6. **Maintainer commitments to confirm.** CONTRIBUTING.md says the project is maintained in spare time with no response commitment, and SECURITY.md points to GitHub private vulnerability reporting; that feature must be enabled in the repository settings.
7. **Duplicate installs.** The Quick Action now prefers `/Applications`, then `~/Applications`, then whatever LaunchServices finds. On a machine with several copies (builds, backups, a disk image) the last step can choose any of them. The first run of the new Quick Action on a two-copy machine has not been observed.
